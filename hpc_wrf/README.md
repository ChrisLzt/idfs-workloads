# WRF 天气预报存储负载

## 来源

本负载以 [NCAR 官方 WRF v4.4 CONUS 2.5km benchmark](https://www2.mmm.ucar.edu/wrf/users/benchmark/v44/benchdata_v44.html) 为数据和业务结构原型。
该案例使用 1501×1201×50 的单域网格，模拟 6 小时天气过程；官方发布包提供初始条件、边界条件、运行配置、日志和参考输出。

WRF 启动时读入初始状态，计算状态主要驻留内存，按指定时次写出 history，并可写入供后续恢复运行使用的 checkpoint。
history 第 0 小时的输出保存初始状态快照，包含已有气象场和静态数据；部分累计量或尚未更新的物理诊断量可以为零。
checkpoint 保存继续积分所需的更多内部状态，不代表本负载包含一次故障恢复。[WRF 官方运行与恢复说明](https://www2.mmm.ucar.edu/wrf/users/wrf_users_guide/build/html/running_wrf.html#restart-capability)

本负载采用8成员集合预报的存储结构：每个成员分别拥有初始场、边界条件、两次history及checkpoint，两份预先核验的只读微物理查找表共享。
[NCAR WRFDA集合生成与成员预报说明](https://www2.mmm.ucar.edu/wrf/users/wrf_users_guide/build/html/wrfda.html#generating-ensembles-with-randomcv)
提供成员状态与输出身份的业务依据。8个成员是本实验的容量选择，不是官方推荐成员数；本测试只构建独立存储身份，不生成或验证科学有效的集合扰动场。

| 来源 | 可核实的配置或建议 | 本负载采用的依据 |
| --- | --- | --- |

| [Appalachian State University 的公开 WRF 服务配置](https://physics.appstate.edu/research/projects/applied-fluids-laboratory/wrf-run-request) | 默认配置列出 27/9/3/1km 四重嵌套，各域均为 `e_vert=60` | 直接支持 1km 与 `e_vert=60` 组合的现实配置依据 |

论文中的“60个层级”未在上述位置给出原始 `e_vert` 参数，不据此认定其质量层与交错层的具体计数。
本负载的精确定义依据 [NCAR 参数说明](https://www2.mmm.ucar.edu/wrf/site/users_guide/namelist_variables.html#domains) 和 [输出维度说明](https://www2.mmm.ucar.edu/wrf/site/users_guide/output_variables.html)：
`e_vert=60` 对应 **59个质量层、60个垂直交错层面**。这些资料证明参数选择具有应用依据，不证明当前完整网格是官方发布的算例，也不代表其业务采用率。

## 数据原型与容量

当前负载采用由上述原型推导的 **1km、e_vert=60 网格**，同一水平范围的网格从 1501×1201×50 细化为 **3751×3001×60**。
两个水平方向的区间数各变为原型的2.5倍，质量点维度从1500×1200变为3750×3000，交错维度各多一个点。
垂直参数由`e_vert=50`增至60：质量层`bottom_top`从49增至59，交错层`bottom_top_stag`从50增至60；两类数组分别计算，不能全部统一乘1.2。
字段类型、其他维度与边界时间记录保持不变。这是一套依据官方字段结构推导的合成容量模型，不是NCAR发布的1km CONUS benchmark，也不是重新运行并验证过的天气模拟。

3751×3001 的推导保持原投影与地理定位下的水平范围：

- 东西向：`(1501−1)×2.5km = (3751−1)×1km = 3750km`。
- 南北向：`(1201−1)×2.5km = (3001−1)×1km = 3000km`。

这里减一是因为交错边缘点比网格单元多一个，见 [NCAR 网格教程](https://www2.mmm.ucar.edu/wrf/wrf_tutorial/nested.html)。
3750×3000km 是投影平面上的名义范围，实际地表距离还受地图比例因子影响；长宽比为1.25。
[NCAR 区域设计说明](https://www2.mmm.ucar.edu/wrf/site/documentation/namelist.wps_best_practices.html) 建议 `dx=dy`，不要求整个计算域为正方形；矩形形状沿用原 CONUS 案例。

初始场、边界条件、history 和 checkpoint 统一根据已核验科学数组的细化后 shape×dtype 汇总无压缩字段量；微物理查找表保持官方文件长度。
主场数组主要随水平面积及其实际垂直维度增长，边界数组随边长及对应垂直维度增长，标量不变，因此不将原物理文件长度统一乘一个系数。
两份 history 使用相同的字段容量模板，保留不同文件身份和独立对象区间。
第 0 小时的独立文件未在发布包中保留，因此其容量采用末时次字段结构的代表值，不是第 0 小时原文件长度的实测结果。

| 文件角色 | 数量 | 对齐前的单份代表容量 |
| --- | ---: | ---: |
| 初始场 | 每成员1份，共8份 | 约 57.669 GiB |
| 已核验的微物理查找表 | 2份，全部成员共享 | 合计约 0.278 GiB |
| 边界条件 | 每成员1份，共8份 | 约 0.777 GiB |
| history：第 0、6 小时 | 每成员2份，共16份 | 约 57.921 GiB |
| checkpoint：第 5 小时 | 每成员1份，共8份 | 约 223.465 GiB |

所选查找表是原日志与发布清单可对应的 `qr_acr_qsV2.dat`、`freezeH2O.dat`。
未取得同名参考文件的 qgV3 表不编造容量。边界条件采用细化后的无压缩字段容量作为同一合成模板，在两个相关阶段读取，不宣称复现了压缩文件中各时次的真实偏移。

单成员主模板合计约 **398.030 GiB**；4KiB请求对齐、每个逻辑文件独占完整4MiB对象后，单成员库存为427,391,188,992字节，包含301,989,888字节的两份查找表对象区间。
8成员科学状态/输出分别独占对象，而查找表只存一份，容器容量为
`8 × (427,391,188,992 − 301,989,888) + 301,989,888 = 3,417,015,582,720`字节，
即 **3.107757568 TiB**，合计 **42个逻辑文件身份、814,680个对象位置**。
这表示完整物化后的库存，不是已经实测触达的对象数。容量不包含NetCDF元数据与压缩存储差异，也不代表原案例物理文件的原样复制。

### 来源依据与合成设计的边界

官方案例提供字段结构、参考文件和启动、history、checkpoint 等业务角色；公开配置与论文提供网格参数的应用依据。
**3751×3001×60 的组合、8成员数量、细化后容量、两次history的选择、600秒四阶段预算、对象级Zipf(0.99)、请求大小及容器映射均属于本负载的合成设计。**
本负载不声称重现上述论文的完整模拟配置、原生I/O频率或真实trace；这些来源也没有测得本负载的3.108TiB容量或814,680个对象位置。

## 四个业务阶段

| 测试时间 | 时长 | 业务 | 读写内容 |
| --- | ---: | --- | --- |
| 0–60 秒 | 60 秒 | 启动 | 读取8个成员初始场与两份共享查找表 |
| 60–150 秒 | 90 秒 | 第 0 小时输出 | 写8个成员初始history，穿插各成员边界读取 |
| 150–510 秒 | 360 秒 | checkpoint | 写8个成员第5小时checkpoint，穿插各成员边界读取 |
| 510–600 秒 | 90 秒 | 结尾输出 | 写8个成员第6小时history |

第 3 小时 history 已省略；第 3 小时边界更新合并到 checkpoint 大阶段。
同一角色的8个成员文件使用相等权重，成员内文件选择按4KiB对齐后的代表容量计算；两份共享表的启动读取权重各累加8个成员的份额。
两个混合阶段也按代表容量选择边界读与输出写，边界读请求概率分别约 **1.323%**、**0.346%**，与单成员设计保持一致。
这些是合成请求权重，不是原 trace 的实测读写比例，也不是字节配额。
输出期间不读取已完成的 history，不加入后处理或恢复读取。

模拟时次与测试秒数分开描述：600 秒压缩了内存计算等待，保留主要文件角色及四段业务活动。
阶段时间、合并后的边界读写和相对持续时间均是本负载的设计参数，并非 NCAR 对所有 WRF 运行的统一要求。

## 对象冷热分布

当前活动文件内部的全部对象参与 **Zipf(0.99)**，不预先划定固定热池。
排名按固定种子排列，并在阶段内保持不变；不同成员使用不同排名种子，同一成员的两份history使用相同的相对区域排名，但实际对象互不重叠。
随着活动切换，热点从初始输入移动到初始 history、checkpoint 和最终 history；已完成的 history 退出活动集合。

保持 `object_size=4MiB`、`stripe_unit=4MiB`、`stripe_count=1`。每个逻辑文件独占一组完整对象，运行请求不进入文件之间的对齐预留区。
单次请求最大 1MiB，作为明确的合成访问参数；在所选对象内随机选择子块，尾块按合法范围缩短并保持 4KiB 对齐。
4MiB 是对象布局粒度，不是原 WRF 每次请求的固定大小。

使用原版 Vdbench 5.04.06 的独立 User 扩展，单个 600 秒 RD，内部按 1 秒判断所属业务阶段，`iorate=max`，不设逐秒配额。
同一阶段跨秒复用固定的频率分布，不逐秒重排热点。`current` 与 `baseline` 是同一套已选 Zipf 方案的兼容入口。

这是 **WRF 结构驱动的合成存储 I/O**。官方材料提供数据结构与业务依据；Zipf、重复区域写入和 600 秒安排由实验添加，不称为原生 WRF trace。
固定时长内不保证覆盖所有对象或完整写完每份快照；实际读写量、对象触达和冷热指标需要运行后测量。
